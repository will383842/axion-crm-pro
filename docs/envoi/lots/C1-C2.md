# Lot C1-C2 — rattachement automatique de la personne née d'une demande (parties C1 et C2)

Suivi : #784, commentaire « PLAN C1-C2 ». Cette PR est la PR-1 du plan : **C1 seulement**. C2 (`SiteSyncIngestService`) vient dans une seconde PR, créée depuis `main` après la fusion de celle-ci.

## Comportement
- Quand le dossier client de la console arrive avec un contact portant une `person_key`, le CRM lie la personne née d'une demande sans SIREN à ce contact, puis rattache à la fiche ses demandes en attente (même clé).
- `pending_match` est gardé sur la demande (historique) ; `payload.arbitrage.attached_by = 'automatique:dossier_client'`.
- Rien n'est déplacé : une personne déjà liée à une autre fiche, opposée (`opposition_at` ou `opt_out`), ou dont le contact porte une autre clé reste intacte (raisons `personne_liee_ailleurs`, `personne_opposee`, `person_key_divergente` dans le journal).
- Drapeaux `personnes_enabled` et `demandes_personne_enabled` fermés : aucune requête sur `personnes`, aucun verrou. Le solde des demandes exige `demandes_personne_enabled`.
- Verrou de transaction par personne pris avant `rapprocher()`, clés triées (pas d'interblocage entre deux dossiers).
- Le chemin d'arbitrage humain (`appliquerApresArbitrage`) ne lie rien (coupé, voir le plan §5).

## Fichiers

## Partie C2 (PR-2) — `SiteSyncIngestService::upsertBusiness` sans SIREN

Suivi : #784, commentaire « PLAN C1-C2 », § 6. Branche créée depuis `main` après la fusion de C1 (#785) ; elle réutilise `SoldeDemandesEnAttente::verrouillerPersonnes`.

### Comportement
- Une demande sans SIREN est rattachée **seulement si** la personne (même `person_key`) est contact **actif** d **une seule** entreprise active, lue sur `contacts` (contact ou fiche à la corbeille : ne compte pas).
- Si la personne est déjà liée à un contact d'une autre fiche : rien, la demande reste en attente.
- **Aucun appel à `upsertCompany` ni `upsertContact`** : aucune valeur déclarée sans SIREN (dénomination, code postal, nom, téléphone) n'est écrite sur la fiche ni sur le contact. Seuls `lierPersonne` (si `contact_id` est nul), l'activité et les étiquettes de provenance sont écrits.
- L'activité sort de la file (`subject_type = company`, `subject_id`, `contact_id`), `pending_match` est **gardé**, `payload.arbitrage.attached_by = 'automatique:personne_connue'`. Statut rendu : `updated`.
- Personne écartée (`opposition_at` ou opposition générale) ou plusieurs entreprises ou aucune : retour **exactement** comme avant, `[null, null, PENDING_MATCH, null]` (piège `attachTags`).
- Drapeau des demandes fermé : `concerneUneDemande` rend faux, **aucune requête**, aucun verrou.
- Verrou de transaction par personne pris avant `assurerDepuisDemande`, donc avant tout verrou de ligne.
