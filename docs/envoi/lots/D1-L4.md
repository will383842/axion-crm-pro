# D1-L4 — verrou par boîte, délai de grâce, délais réseau, borne de temps

Cahier : `docs/envoi/lots/D1-D2-cahier.md` (PR #617), sections 0 et 5. Préalables fusionnés : D1-L1 (#620), D1-L3 (#629), D1-L2 (#634).

- `ReleveImap::relever` et `::rattraper` : verrou de session `pg_try_advisory_lock(hashtextextended('envoi:releve:<espace>:<boîte>', 0))`,
  libéré dans un `finally`. Non obtenu : `BoiteOccupee` (message fixe), rien n'est lu ni écrit.
- `ReleveImapCommande` : `BoiteOccupee` est comptée (`occupee`), jamais une panne (code 0). Borne `BORNE_SECONDES = 45` (horloge `now()`) :
  passée la borne, aucune nouvelle boîte n'est commencée (`hors_borne`). La sortie finit par `occupee=N hors_borne=N echecs=N`.
- `ReleveImap::relever` seulement : `DELAI_GRACE_SECONDES = 180`. Un message reçu depuis moins de 180 s (et ceux qui le suivent) est relu au
  passage suivant ; le curseur reste sur l'UID qui le précède. Une date dans le futur est « récente » jusqu'à 24 h, au-delà le message est
  traité (pas de blocage sans fin). `rattraper` n'est pas touché.
- `LecteurBoiteWebklex::protocole()` : `setConnectionTimeout(15)` avant `connect`. La bibliothèque (6.2.0) n'a QU'UN réglage, que
  `createStream` applique à la connexion ET à la lecture du flux : pas de délai de lecture distinct (30 s du cahier non applicable).

Aucune migration, aucun drapeau, aucune configuration, aucune route, aucun fichier chaud. Aucune connexion réelle : lecteurs simulés.
Les fonctions `pg_*advisory*` sont permises au rôle applicatif (G1 et G3 passent sous `pgsql_app` ET propriétaire).
