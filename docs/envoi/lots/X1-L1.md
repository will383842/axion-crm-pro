## Écart au plan (renforcement, à valider)
`envoi_sequence_etapes_figees` prend d'abord un verrou `FOR NO KEY UPDATE` sur la ligne de la séquence (c'était `FOR UPDATE` : il bloquait aussi les contrôles de clé étrangère des gestes et inscriptions). Le déclencheur de liaison lit la séquence `FOR SHARE` (c'était `FOR KEY SHARE`, qui NE conflit PAS avec `FOR NO KEY UPDATE` : le changement des deux est indissociable). Une liaison et une écriture d'étape se sérialisent donc : un ajout d'étape concurrent ne peut pas passer entre le comptage et la pose du lien. Preuve : test « M3 données » (deux sessions réelles, `lock_timeout`) dans les deux sens ; la mutation « lien `FOR KEY SHARE` » le fait rougir.

## Hypothèses et limites des gardes (à lire avant le lot applicatif)
- **READ COMMITTED (F2).** Les gardes supposent le niveau d'isolation par défaut de PostgreSQL, READ COMMITTED (c'est celui de l'application). En REPEATABLE READ ou SERIALIZABLE, l'instantané d'une transaction peut ne pas voir une liaison ou une étape validée entre-temps : la sérialisation par verrou de ligne (étapes / liaison) n'y est pas garantie de la même façon. Ne pas changer le niveau d'isolation de ces écritures sans rejouer les tests de contention.
- **Interblocage possible (F1).** Les verrous pris par les déclencheurs (`FOR SHARE` sur la campagne dans la reprise et à la naissance, `FOR SHARE` / `FOR NO KEY UPDATE` sur la séquence dans la liaison et les étapes) peuvent, selon l'ordre dans lequel deux transactions touchent campagne et séquence, produire un `40P01` (interblocage détecté par PostgreSQL : une des deux est annulée, l'autre aboutit). Le lot applicatif doit **relancer** la transaction annulée (une ou deux fois) et ne jamais traiter `40P01` comme une erreur définitive.
- **Le propriétaire peut désactiver les déclencheurs.** Les gardes sont des déclencheurs : elles valent pour le rôle applicatif ET pour le propriétaire / un superutilisateur qui écrit normalement, mais le propriétaire de la table (ou un superutilisateur) peut les retirer (`ALTER TABLE ... DISABLE TRIGGER`, `session_replication_role = replica`). La phrase « valable pour tous les rôles » est donc à nuancer : elles protègent contre le rôle applicatif et les écritures ordinaires, pas contre un propriétaire qui les désactive volontairement (les tests s'en servent d'ailleurs pour fabriquer des données incohérentes).
- **I2 — `DepotCampagnes::TRANSITIONS`.** Le code applicatif accepte encore `programmee → a_valider` ; la base le refuse pour une campagne reliée. À aligner dans le lot suivant (aucun code applicatif touché ici).
