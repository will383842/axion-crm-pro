## Interprétations (là où le cahier laisse une marge) — à valider par la relecture
1. **Contact de presse seul dans une entreprise.** Les candidats d'une entreprise sont tous ses contacts de type `nominatif` ; un contact de presse reste candidat et porte le motif `presse`. Une entreprise dont le seul nominatif est un journaliste est donc comptée `presse` (pas `sans_contact`). Les deux lectures excluent ; celle-ci garde le motif exact.
2. **SIREN opposé au niveau de la fiche.** Une entreprise dont le SIREN est au registre est comptée `opposition` même si elle n'a aucun contact (avant `sans_contact`).
3. **Entreprise déjà en séquence** (inscription active sur un autre contact) : le motif s'applique à chaque candidat, selon l'ordre de `PRIORITE` (un candidat opposé reste `opposition`). Sans candidat : `sans_contact`.
4. **Un membre = une unité de comptage** (`membres`), y compris les entreprises « déjà couvertes ».
5. **Erreur de base hors exclusions** (par ex. lecture des membres) : `QueryException` enveloppée dans `lecture_opposition_impossible` (réessayable), `57014` en `lecture_trop_longue`, comme le prévoit le cahier.

## Limites
- **Test 13b** sort de l'enveloppe transactionnelle de `RefreshDatabase` (`DB::rollBack()`) pour observer le cas « appelant sans transaction » (seul cas où `READ ONLY` est émis : en transaction imbriquée on n'altère pas la transaction de l'appelant). Il n'écrit ni ne lit aucune donnée (campagne inconnue) : rien à nettoyer.
- **« Type inconnu » de cible** (dont « personnes ») : la contrainte CHECK de `envoi_campagnes.cible` refuse tout type hors liste/audience/etiquette/carnet, donc on ne peut pas fabriquer une telle campagne en base ; la branche `default` → `cible_introuvable` n'est couverte que par lecture du code (et les références invalides, elles, sont testées).
- **`57014` → `lecture_trop_longue`** : convertie par le code, mais aucun test ne provoque un vrai dépassement de délai (pas de requête lente fabricable sans `pg_sleep` dans la sélection). Seule la fabrique est testée.
- Le dédoublonnage ne vaut que DANS un lot ; l'unicité entre lots viendra du « déjà en séquence » une fois L4 écrit. **Index manquant** `envoi_inscriptions (workspace_id, empreinte_adresse) WHERE statut='active'` : la requête par empreinte reste correcte mais non indexée ; l'index (et l'unicité) fait l'objet d'un lot de migration séparé, avant L4 (arbitrage du pilotage).
- `StatutOpposition` est utilisé tel quel, il lit désormais `personnes.opposition_at` (P0 fusionné).
- **Taille de la PR** : la règle « 250 à 400 lignes » ne peut pas tenir, le cahier impose 4 classes, 21 tests et ce document ; écart assumé et signalé dans la PR.
- Contrôles locaux : base PostgreSQL 16 avec PostGIS et pgvector ; `pg_partman` absent (la migration le tolère, avertissement journalisé).
